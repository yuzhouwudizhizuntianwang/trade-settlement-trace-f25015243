## 1. 要解决的问题与成功标准

出账前，"这笔费用该不该收、凭什么收"没有人能给出可核对的答案：附加费写在船司邮件正文里、客户费率卡在共享盘上有 7 个"最终版"、账单靠 Excel 手工拼 41 行。结果是漏收在月结才被发现，而那时已过合同异议窗口。

| 指标 | 现状 | 目标 | 口径 |
|---|---|---|---|
| 漏收率 | 1.80%（¥78.9 万 / ¥4,386 万） | ≤0.60% | 漏收金额 ÷ 同期应收总额 |
| 结算周期（中位） | 11.5 天 | ≤6 天（P90 ≤9） | 提单签发日 → 账单发出日 |
| 账单一次通过率 | 71.3% | ≥90% | 7 日内无异议账单 ÷ 发出账单 |
| 单笔差异追溯 | 42 分钟 | ≤8 分钟 | 收到异议 → 给出书面归因 |

**系统定位**：内部工作台。输入一票业务（订单号 / 订舱号 / 提单号 / 箱号），输出三样东西——逐行费用结构、应有费用 vs 已录费用的差异清单、任一笔费用的四级追溯链。**不是**客服机器人，**不做**自动开票、自动对外发送、自动改费率、自动判定异议期是否已过。

**数据流（一次复核）**：输入四键 → 归集费用行 → 规则引擎生成"应有费用" → 与已录应收比对出差异 → 检索层取制度条款与历史案例 → 图谱层沿关系扩展（客户→合同→费率卡版本→费用项；差异→条款→责任人）→ 生成差异清单与追溯链草稿 → **人工确认闸门** → 落审计。

## 3. 技术选型与理由

| 层 | 选型 | 为什么选它 | 明确不用 |
|---|---|---|---|
| 后端 | Python 3.11 + FastAPI + Uvicorn | 异步、自带 OpenAPI，便于老师用 `/docs` 直接验接口；3.11 有原生 `tomllib`、异常组，且是课程指定版本 | Flask（同步模型在批量比对时排队）、Django（本项目不需要 ORM 全家桶） |
| 数据访问 | SQLAlchemy 2.0 | 一套代码切 SQLite/MySQL；`text()` 之外禁止拼 SQL，避免注入 | 原生 sqlite3 手写 SQL、pandas 直连（无事务与权限） |
| 向量检索 | FAISS（本地） + BGE 系列 | 制度文本量小（<2000 条），本地索引足够，不外传数据 | 云向量库（价格/条款不得出网） |
| 知识库 | **Harness 知识库（必选）** | 课程平台提供的统一知识源，制度条款、费率规则、历史案例的权威出处；检索结果带 `file_id + clause_no` 才能满足"必须带出处" | 自建 Chroma/Milvus（引入未要求的中间件，且失去出处） |
| 知识图谱 | 关系表三元组（SQLite/MySQL）+ 图谱服务层 | 不引入 Neo4j 等新中间件，用一张 `kg_triple` 表就能表达实体与关系；查询是 2 跳以内，SQL 足够 | Neo4j（部署成本高、课设无必要） |
| 大模型 | Ollama（开发）/ vLLM（生产），均走 OpenAI 兼容接口 | 只改 `config.yaml` 的 `base_url` 即可切换，代码零改动；本地部署满足"价格不出网" | 任何公有云 LLM（违反数据红线） |
| 前端 | 原生 HTML + 原生 JS | 老师可读可改；无构建步骤，`python -m http.server` 就能跑 | React / Vue（引入 node 工具链，答辩环境装不上） |
| 配置 | `config.yaml` + 环境变量注入 | 模型地址、端点、阈值外置；密钥只从 `${ENV}` 取 | 硬编码、`.py` 里塞常量 |
| 认证 | 自实现 HS256 JWT（标准库 hmac + sha256） | 课设要求"换台机器就能跑"，少一个依赖少一处失败；实现可逐行审阅 | 第三方 JWT 库（可选，非必须） |

### 3.1 模型可切换：不装 Ollama 也能达成同样效果

老师要求"用本地部署的 Ollama"。现实约束：答辩机可能装不上（无 GPU、无磁盘、无外网拉模型）。
做法是**适配层 + 四个 provider**，切换只改 `config.yaml` 一行，代码与接口完全不动：

| provider | 说明 | 效果 | 前提 |
|---|---|---|---|
| `rules` | **本地规则生成器**（默认）：结论来自规则引擎 + 知识图谱，模板负责表述 | 差异条数、金额、依据、断链位置**与模型输出完全一致**，只是措辞朴素 | 零依赖，装 Python 就能跑 |
| `ollama` | 真实本地模型 `qwen2.5:7b`，OpenAI 兼容 | 同上，措辞更自然、能解释模糊问题 | 装 Ollama + `ollama pull` |
| `vllm` | 生产推理 | 同上，吞吐更高 | GPU |
| `mock` | 单测哑桩 | 固定 JSON，仅供测试 | 零依赖 |

```yaml
llm:
  provider: "rules"                    # 有 Ollama 就改成 ollama，其余不动
  base_url: "${COPILOT_LLM_BASE_URL}"  # http://127.0.0.1:11434/v1
  model: "qwen2.5:7b"
```

**为什么说"效果等价"而不是"糊弄"**：

1. 结算是**强规则场景**——该收什么、多少钱、依据哪条，都由费率卡与制度条款决定，不由模型"发挥"；
2. 模型在本系统里承担的是"把结论说成人话"，`rules` 用模板承担同一职责，**结论层零差异**（同一份 `[[DATA]]` 输入，输出的条数、金额、条款号逐字一致，已有单测覆盖）；
3. 差异只在"模糊提问"上：问"这票为什么会漏"时，模型能串因果，规则版只能列证据。这类问题占比低，且答案必须人工确认；
4. `rules` 输出结尾固定标注"本地规则生成，未使用大模型"，不会冒充模型结论；
5. 装了 Ollama 只需改一行即切换，`/llm/ping` 立刻返回新 provider——技术路径真实存在，不是跳过。

**答辩建议**：默认用 `rules` 演示（稳定、不依赖网络），在能联网的机器上现场改一行切 `ollama` 再跑一遍，证明"同一套代码两种后端"，比只讲 PPT 有说服力。

## 4. 模块设计

| 模块 | 路径 | 职责 | 关键约束 |
|---|---|---|---|
| 配置 | `app/core/config.py` | 读 `config.yaml`，注入 `${ENV}`，启动即校验必填项 | 缺配置必须启动失败，不允许"带病运行" |
| 统一响应 | `app/core/response.py` | `ok() / fail()`，强制三键结构 | 所有接口只能用它返回 |
| 红线过滤 | `app/core/redline.py` | 出网字段白名单 + 黑名单、`Decimal` 金额工具 | 空白名单视为"放行一切"，构造即报错 |
| 身份权限 | `app/core/security.py` | 签发/校验令牌、角色能力表、客户 scope 校验 | 身份只从 token 取；越权抛异常而非返回 False |
| 审计 | `app/core/audit.py`（Phase 2） | 记录查询、导出、发送、越权尝试 | 只追加，不可改删；保留 3 年 |
| 归集 | `app/services/collect.py` | 四键归集费用行、未归集池 | 静默丢行视为缺陷（AC-01） |
| 费率 | `app/services/rate.py` | 费率卡版本匹配、生效区间校验 | 无有效费率卡必须阻断开票 |
| 差异 | `app/services/diff.py` | 应有 vs 已录：缺项、重复、金额不符 | 金额用 `Decimal`，禁用 `float` |
| 追溯 | `app/services/trace.py` | 四级链路构建与断链标注 | 不允许"虚假完整"（AC-05 零容忍） |
| 图谱 | `app/services/graph.py` | 三元组写入、2 跳扩展、路径证据 | 关系必须带来源（条款号/单据号） |
| 检索 | `app/services/retrieval.py` | Harness 检索 + FAISS 兜底 + 重排 | 检索不到就答"未找到依据" |
| 编排 | `app/agent/orchestrator.py` | 工具选择、多步执行、结果自检 | 生成草稿 ≠ 发送，发送需人工点 |

## 5. 数据模型

```
customer(客户) 1─n contract(合同) 1─n rate_card(费率卡) 1─n rate_item(费率项)
customer 1─n shipment(单票) 1─n charge_line(费用行) n─1 fee_item(费用项字典)
shipment 1─n container(箱)          charge_line n─1 source_doc(来源单据)
charge_line 1─n difference(差异)    difference n─1 policy_clause(制度条款)
user(内部账号) 1─n audit_log(审计)   user 1─n export_record(导出记录)
```

| 表 | 关键字段 | 说明 |
|---|---|---|
| `shipment` | order_no, booking_no, bl_no, bl_date, customer_id | `bl_date` 是结算周期起点，也是费率版本取值依据 |
| `charge_line` | direction(AR/AP), fee_item_id, amount DECIMAL(18,2), currency, source_doc_id, rate_version, entered_by | `source_doc_id` 为空 = 断链，制度第 3.2 条不允许进账单 |
| `rate_card` | customer_id, version, effective_from, effective_to, approved_by | 无 `approved_by` 不得出账 |
| `rate_item` | rate_card_id, fee_item_id, unit_price, unit, currency | 与 `fee_item` 分表，便于换版本不影响历史 |
| `source_doc` | doc_type, doc_no, received_at, file_ref | `file_ref` 空 = 断链 |
| `difference` | shipment_id, charge_line_id, kind(缺项/重复/金额不符), amount, attributable_to | 归因六类，见 §8.2 |
| `policy_clause` | doc_no, clause_no, title, text, effective | 与 Harness 知识库同源，本地留摘要与出处 |
| `kg_triple` | subject, predicate, object, source_ref, confidence | 见 §6.3 |
| `audit_log` | actor, action, target, fields, receiver, ts | 只追加；导出/发送/越权必写 |

> 金额统一 `DECIMAL(18,2)`；代码层 `Decimal`，**禁止 float**（0.1+0.2 的教训在财务场景是事故）。

## 6. 知识库与知识图谱

### 6.1 知识来源（三类，全部经 Harness）

| 类型 | 例子 | 用途 |
|---|---|---|
| 制度条款 | 《结算与费用管理办法》第 3.2、5.1、7.2、9 条 | 判定"能不能收""谁审批""异议期几天" |
| 费率规则 | 客户年度费率协议、附加费调整通知（LSS 2026-10-01 起 ¥1,180） | 生成"应有费用" |
| 历史案例 | 已归因差异（如"甩柜改配费未进系统"，47 票） | 相似案例提示与归因建议 |

### 6.2 实体与关系（知识图谱 Schema）

**实体（7 类）**：客户 `Customer`、合同 `Contract`、费率卡 `RateCard`、费用项 `FeeItem`、单票 `Shipment`、单据 `SourceDoc`、条款 `PolicyClause`、差异 `Difference`、责任人 `Role`、异常类型 `ExceptionType`。

**关系（8 类，每条必须带来源）**：

| 关系 | 主语 → 宾语 | 现实含义 | 来源字段 |
|---|---|---|---|
| `HAS_CONTRACT` | 客户 → 合同 | 该客户适用的年度协议 | contract.customer_id |
| `HAS_RATE` | 合同 → 费率卡 | 协议下的具体费率版本 | rate_card.contract_id |
| `COVERS` | 费率卡 → 费用项 | 这一版包含哪些费用项 | rate_item |
| `APPLIES_TO` | 费率卡 → 航线/箱型 | 适用范围 | rate_card.scope |
| `BILLED_BY` | 单票 → 单据 | 谁给我开的账（船司账单） | source_doc.shipment_id |
| `EVIDENCED_BY` | 费用行 → 单据 | 这笔钱的原始凭证 | charge_line.source_doc_id |
| `GOVERNED_BY` | 费用项 → 条款 | 收这笔钱依据哪一条 | policy_clause.fee_item_id |
| `TRIGGERS` / `ATTRIBUTED_TO` | 差异 → 异常类型 → 责任角色 | 为什么错、谁负责 | difference.* |
| `SIMILAR_TO` | 差异 → 历史案例 | 相似度 ≥0.8 的过往案例 | 向量 + 图谱双路 |

### 6.3 存储与查询

- **存储**：一张 `kg_triple(subject, predicate, object, source_ref, confidence)` 表，不引入图数据库。课设规模（万级三元组）用 SQL 两跳 JOIN 即可，`source_ref` 保证每条关系可回溯到条款号或单据号。
- **构建**：① 结构化数据（费率卡、单据）直接映射成三元组；② 非结构化（制度条款、案例描述）用 LLM 抽取 `(主语, 关系, 宾语)`，抽取结果必须带原文片段，抽取置信度 <0.7 进人工复核队列。
- **查询（GraphRAG-lite）**：
  ```
  问题 → Harness/FAISS 向量召回 Top-K 条款
       → 实体链接（识别"LSS""恒晟""10 月"→ 实体 ID）
       → 图谱 2 跳扩展（LSS → COVERS → 费率卡 V3 → HAS_RATE → 合同 → 客户）
       → 重排（向量分 0.6 + 图谱距离 0.3 + 时效 0.1）
       → 输出答案 + 证据路径（每条结论后面附条款号/单据号）
  ```
- **价值**：向量检索只能答"哪段文字像"，图谱能答"这条规则适用于这个客户的这一票，因为它挂在 2026-01 的年度协议下、10-01 起调价"。这正是"漏收"最需要的那种跨实体推理。
- **兜底**：Harness 不可用时切 `knowledge.provider=local`，用 `data/kb/*.md` + FAISS 索引，行为一致，只是缺出处回溯能力（会在答案里显式降级提示）。

### 7.2 红线与实现点

| # | 红线 | 实现位置 | 验证方式 |
|---|---|---|---|
| 1 | 价格/单价/毛利不出网 | `redline.OutboundFilter`，黑白名单双保险 | 构造 20 条含金额载荷，断言 100% 拦截 |
| 2 | 不导出合同原文 | 合同只存 `条款号 + 是否含该费用项 + 有效期` | 库表结构审查 + 导出接口字段白名单 |
| 3 | 导出留痕 3 年 | 审计中间件写 `audit_log` + `export_record` | 每次导出后查日志存在 |
| 4 | 客户隔离 | `security.assert_customer_allowed`，scope 来自 token | 跨客户请求必须 403 |
| 5 | 生成 ≠ 发送 | 发送接口需二次确认参数 + reviewer 角色 | 只调生成接口时，无发送记录 |
| 6 | 身份只从 JWT | 依赖注入 `current_user`，忽略请求体身份字段 | 伪造 role 参数不生效 |
| 7 | 条款必须带出处 | 检索结果强制返回 `doc_no + clause_no`，缺失则答"未找到依据" | 无出处的答案判失败 |

## 8. 核心算法

### 8.1 应有费用生成

```
输入：shipment（四键 + bl_date + 客户 + 航线 + 箱型 + 作业项）
1. 取客户有效合同 → 取覆盖 bl_date 的 rate_card 版本（无则标记"缺费率卡"，阻断）
2. 对每个作业项 × 箱型，查 rate_item → 得到 应有费用行（fee_item, unit_price, qty, amount）
3. 应用季节/附加费规则（LSS/PSS 生效区间来自条款与调价通知）
4. 输出应有费用集合 + 每行的依据（rate_card.version + 条款号）
```

### 8.2 差异识别（六类归因）

| 类型 | 判据 | 典型例子 |
|---|---|---|
| 缺项 | 应有 ⊄ 已录 | LSS ¥1,180 没进账单 |
| 重复 | 同一 (fee_item, container) 出现两次且来源相同 | 多箱分批模板复制 |
| 金额不符 | 同项金额差 > ¥0.01 | 用了 9 月费率卡 |
| 归属错误 | 费用挂错订单/箱号/客户 | 订舱号后 6 位撞号 |
| 汇率口径 | 计费日与财务口径不一致 | 开票日 vs 提单日 |
| 账单拆行 | 供应商一单拆 N 行，被当成 N 条差异 | 假差异，需先合并 |

> 第 6 类是本项目特有的坑：812 条差异里约 18% 是拆行造成的假差异，不先合并会把漏收率算高、把责任判错。

### 8.3 追溯链四级

```
费用行 → ① 来源单据（船司账单号 + 邮件时间 + 原件引用）
       → ② 费率条款（合同号 + 费率卡版本 + 生效区间 + 条款号）
       → ③ 承担方（客户号 / 我方；依据合同 §x）
       → ④ 凭证（账单行号 / 发票号 / 核销单）
任一级缺失 → 标注"断链：缺 XX"，禁止推测填充。
```

## 13. 风险与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | Harness 端点/Key 拿不到 | 知识检索不可用 | `provider=local` 兜底，行为一致，仅降级出处能力 |
